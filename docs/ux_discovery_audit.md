# Manny's FPL House — Current UX Discovery Report

**Audience:** Lead UI/UX Designer
**Purpose:** Document the existing application so the redesign is based on reality.
**Scope:** Frontend + UX discovery audit. No code was modified.
**Date:** August 2026
**Status:** Read-only audit (file references throughout point at the existing implementation).

---

## 1. Application Structure

### 1.1 Entry Points & Framework

| Item | Detail | Reference |
|---|---|---|
| Frontend framework | **Streamlit 1.60** (single-page Python server, auto-rerun model) | `requirements.txt` |
| Dashboard framework | Streamlit multipage app — one file per page | `app.py`, `pages/` |
| Charting | **Plotly 6.9** (graph_objects + express) rendered via `st.plotly_chart` | `requirements.txt`, `components/theme.py` |
| Styling | Custom **CSS injected via `st.markdown(unsafe_allow_html=True)`** + `.streamlit/config.toml` dark theme | `components/theme.py:83`, `.streamlit/config.toml` |
| Data layer | SQLite via SQLAlchemy (`data/moneyball.db`), Alembic migrations | `database/database.py:17`, `alembic/` |
| Backend | All in-process Python — no server/client separation, no REST API | `services/`, `engines/`, `features/` |
| Auth | **None** — open, single-user (default team ID `472930`) | `utils/constants.py:56` |

### 1.2 Navigation Structure

Navigation is **auto-generated by Streamlit** from `pages/N_*.py` filename prefixes. There is no hand-built nav, no page hierarchy, no grouping, and no cross-page linking.

```
⚽ Manny's FPL House
 ├── app.py ................ "About" (home / hero)          [brand + data bootstrap]
 └── pages/
     ├── 1_My_Team.py ............. My Team          [personal squad dashboard]
     ├── 2_Player_Rankings.py ..... Player Rankings  [player table + market activity]
     ├── 3_Team_Analysis.py ....... Team Analysis    [20-club aggregate comparison]
     ├── 4_Team_History.py ........ Team History     [season + gameweek breakdown]
     ├── 5_Player_Comparison.py ... Player Comparison[head-to-head player tool]
     ├── 6_Assistant_Manager.py ... Assistant Manager[decision engine / recommendations]
     ├── 7_Model_Analytics.py ..... Model Analytics  [validation platform, engineering]
     └── 8_Model_Comparison.py .... Model Comparison [V3 shadow model vs V2 evaluation]
```

### 1.3 Shared Page Scaffold (identical on every page)

```
Sidebar ──┬─ "Data updated Xh ago" caption      (components/sidebar.py:16)
          ├─ [Refresh Data] button              (components/sidebar.py:26)
          └─ (page-specific filters, e.g. Player Rankings)
Body ─────┬─ page_header(title, subtitle)       (components/theme.py:406)
          ├─ section_label() + divider() separators (components/theme.py:415/425)
          └─ metric cards, charts, tables, cards (stacked vertically)
```

Every page calls: `st.set_page_config(layout="wide")`, `inject_theme()`, `ensure_data_loaded()`, `render_refresh_button()`, then fetches data via `get_session()`.

### 1.4 User-Accessible Workflows (entry points)

1. **Browse/Explore** — Player Rankings (2), Team Analysis (3), Player Comparison (5)
2. **Personal dashboard** — My Team (1)
3. **Decide** — Assistant Manager (6): transfers, captaincy, chips
4. **Engineer/Validate** — Model Analytics (7): weekly ingest + validation cycle
5. **Evaluate the shadow model** — Model Comparison (8): V2 vs V3 xPts

## 2. Page Audit

> Question each page answers is stated; "User Goal" = the decision it supports.

### 2.1 About — `app.py`

- **Purpose:** Branded landing/hero page; communicates what the platform is; triggers data bootstrap.
- **User goal:** *"What is this, and is it ready?"*
- **Components:** HTML hero title, icon row, 4 static feature cards (`app.py:78`), "Data loaded & ready" badge (`app.py:109`).
- **Data displayed:** None (static copy).
- **UX concerns:**
  - Feature cards are **not clickable** — dead ends that look like CTAs.
  - Hero text confesses it is a "personal project by a beginner" (`app.py:53`) — fine for authenticity, but sets low trust expectations for a data platform.
  - No evidence/validation story told here despite it being the platform's core philosophy.

### 2.2 My Team — `pages/1_My_Team.py`

- **Purpose:** Personalised squad dashboard; live squad, captaincy, transfers.
- **User goal:** *"What is my squad? Who should be captain? What have I done lately?"*
- **Components:**
  - 4 metric cards: Overall Points, Overall Rank, GW Points, GW Rank (`1_My_Team.py:77`)
  - Gameweek **selectbox** (drives the squad shown) (`:104`)
  - **Pitch chart** (Plotly) with formation layout, red player markers, (C)/(VC) badges, hover with name/team (`:124`)
  - **Bench** dataframe (Player/Team/Pos/Price/Pts/xGI) (`:180`)
  - **Captain Recommendation** dataframe + `st.info` summary (`:196`)
  - **Transfers** dataframe (in/out/date) (`:226`)
- **Data displayed:** Manager profile, squad picks per GW, captain/vice-captain flags, value scores, transfers.
- **UX concerns:**
  - Captain recommendation explains itself with **"Value Score", not projected points** — inconsistent with the captain engine and unexplained (`:203`).
  - The pitch is interactive but non-actionable: hovering only shows name/team; no stats, no fixture, no "why".
  - No fixture context anywhere — you can't see who your squad plays this GW.
  - Two unlabelled/unexplained dataframes ("Pts", "xGI") with no column metadata.
  - Value Score appears with zero explanation ("0.0–100?").

### 2.3 Player Rankings — `pages/2_Player_Rankings.py`

- **Purpose:** Full-pool player table + market activity + price movers.
- **User goal:** *"Which players should I buy/sell/watch?"*
- **Components:**
  - **Sidebar filters** (the only filtered page): club multiselect, position multiselect, max price slider, min minutes slider, min/max ownership sliders (`components/sidebar.py:37`)
  - 4 metric cards: Players, Avg Value Score, Highest Value Score, Avg Ownership (`2_Player_Rankings.py:64`)
  - **Market Activity:** "Most Transferred In/Out" — duplicated as horizontal bar chart **and** table, each with a "Show top [5/10/20]" selectbox (`:74`)
  - **Market Movers:** "Biggest Price Rises/Drops" horizontal bars (`:148`)
  - **All Players** sortable table via `render_player_table` with sort selectbox + ascending checkbox (`:213`)
- **Data displayed:** ~10 player columns (name/team/pos/price/mins/pts/xGI/xGI90/own%/value) + transfers in/out + price changes.
- **UX concerns:**
  - **Extremely long scroll** — ~8 stacked chart/table blocks before the main table.
  - Sidebar filter sliders use `label_visibility="collapsed"` (`components/sidebar.py:81`) → **labels rendered invisible**; users see unlabelled sliders grouped only by small HTML headings.
  - Charts + tables **duplicate the same data** side-by-side.
  - "Value Score" everywhere, never explained.
  - Two identical-looking "Show top" selectboxes next to each other — ambiguous which controls which chart.

### 2.4 Team Analysis — `pages/3_Team_Analysis.py`

- **Purpose:** Aggregate club comparison.
- **User goal:** *"Which clubs are strong/cheap/productive?"*
- **Components:** Team summary table (`render_team_table`), then 5 stacked vertical bar charts (Total Points, Total xGI, Avg Price, Squad Size, Avg Value Score) via `style_px_chart`.
- **Data displayed:** team_name, player_count, avg_price, total_points, avg_points, total_minutes, avg_xgi, total_xgi.
- **UX concerns:**
  - Pure data-dump; 6 stacked sections with no narrative or conclusion.
  - 45°-rotated x-axis team names on every chart (`style_px_chart(xaxis_tickangle=-45)`).
  - Chart heights all identical (380) regardless of content.
  - Value Score appears again with no explanation.

### 2.5 Team History — `pages/4_Team_History.py`

- **Purpose:** Season-by-season + current-season GW breakdown.
- **User goal:** *"How is my season tracking vs previous ones?"*
- **Components:** 4 metric cards (Overall Points/Rank, All-Time Seasons, Best Season Rank), Season points bar + rank line (reversed axis), season details table, GW points bar, cumulative points line, GW details table.
- **Data displayed:** season_name, points, rank, rank %, per-GW points/rank/total.
- **UX concerns:**
  - Charts and tables **duplicate** the same numbers (`:101` + `:144`, `:157` + `:194`).
  - No insight layer — "Best Season Rank" computed but the story (improving/declining) is not told.
  - Reversed y-axis rank trend is labelled "lower is better" but unlabelled axes otherwise.

### 2.6 Player Comparison — `pages/5_Player_Comparison.py`

- **Purpose:** Head-to-head player comparison tool.
- **User goal:** *"Player A or Player B for my team?"*
- **Components:**
  - **Multiselect** player search (max 5) (`:71`)
  - Player **cards** (colored left border) (`:100`)
  - **Stats table** via `st.table` (static, non-sortable) (`:170`)
  - **Radar chart** (6 normalised metrics) (`:205`)
  - **Bar chart** comparison with metric selectbox (`:242`)
  - **Price vs Value scatter** (`:293`)
  - **Fixture difficulty** GW-range slider (`:322`), avg fixture score bar, difficulty **heatmap**, fixture summary table
- **Data displayed:** ~18 stats per player + fixture difficulty per GW.
- **UX concerns:**
  - **Longest page in the app** — 9 stacked sections.
  - `st.table` (static) used here while every other page uses `st.dataframe` (sortable) — inconsistent.
  - Radar normalisation is across *all players in the pool* — technically correct but visually misleading and undocumented.
  - Fixture slider is a latent bug: `min_value=5` with `value=(1, 10)` (`:323`) — Streamlit requires `value >= min_value`, so this raises at runtime.
  - Difficulty heatmap shows opponent short names but no per-GW numbers; fixture summary table shows scores with no scale legend ("Fixture Score 0–100?").

### 2.7 Assistant Manager — `pages/6_Assistant_Manager.py`

- **Purpose:** The decision engine — transfers, captaincy, chips, squad health.
- **User goal:** *"What should I do this week?"*
- **Components:**
  - **Executive Summary** row: squad rating gauge card + plain-markdown summary + squad value/bank/free-transfers card (`:63`)
  - **Transfer Recommendation cards** (player out → in, risk badge, pts gained, value/fixture/minutes/confidence, reasoning) via `render_transfer_recommendation` (`components/recommendation_card.py:10`)
  - **Chip cards** (PLAY/HOLD badge, confidence, best GW, reasoning) ×4 (`:112`)
  - **Squad Breakdown** dataframe (Player/Team/Pos/Price/Pts/Form/xGI90/Value/Rating) (`:130`)
  - Strengths/Weaknesses bullet lists (`:150`), Injuries/Rotation **alerts** (`:169`), Favorable/Difficult fixtures (`:184`), Price movers (`:201`)
- **Data displayed:** squad rating, bank, free transfers, transfer plan, chip plan, per-player ratings, alerts.
- **UX concerns:**
  - **Heaviest page**: runs the full pipeline + assistant on load inside a spinner (`:42`), then renders ~9 sections — a very long scroll.
  - Executive summary is **raw markdown text**, not structured UI; formatting is inconsistent.
  - Strengths/weaknesses/fixtures are plain bullet columns with no visual hierarchy, no counts, no ranking.
  - Alerts (injuries/rotation) are repeated `st.warning` boxes stacked — no severity, no dedup, no action buttons.
  - The reasoning text on cards is data-rich but there is **no link to the player data** behind it.
  - No captaincy recommendation is surfaced on this page even though the captain engine exists (captaincy only lives on page 1 and page 8).

### 2.8 Model Analytics — `pages/7_Model_Analytics.py` (engineering/technical)

- **Purpose:** Validation platform — ingest results, measure accuracy, classify errors, version comparison, weekly report.
- **User goal:** *"Did the model predict well? What went wrong? Can I trust the next prediction?"*
- **Components:**
  - **7 tabs** workflow: Result Ingestion → Scatter → Calibration & Health → Error Analysis → Engine Scorecard → Version Comparison → Weekly Report (`:130`)
  - **Metric cards with inline expanders** explaining MAE/RMSE/Bias/CI coverage in plain language (`:47`, `:91`)
  - Scatter plot (predicted vs actual with MAE offset line) (`:246`), calibration curve (`:352`), MAE trend line (`:408`)
  - Error type pie + severity bar with plain-language explanations (`:481`)
  - Engine scorecard grid (MAE/correlation/signal per engine) (`:574`)
  - Version Comparison (baseline vs treatment, evidence level, `st.json` dump) (`:623`)
  - **Weekly Report** with evidence level, insights, error summary, **Candidate Improvements** expanders (with explicit "recommendation only, human review required" warning) (`:683`)
  - Sidebar: Model Health metrics + numbered Quick Actions (`:806`)
- **Data displayed:** validation metrics (MAE/RMSE/bias/CI coverage), error distributions, engine accuracy, version diffs, weekly report.
- **UX concerns:**
  - **Terminology is engineering-grade** (MAE, RMSE, CI80, coverage, bias, version_id) — the explanations exist but are buried in collapsed expanders.
  - Tab numbering and "Step N" section labels **disagree** (tab "2️⃣ Scatter Plot" contains "Step 2: Review Prediction Accuracy", but Section labels inside jump 1→2→3→4→5→6 with tab 7 "Weekly Report" labelled Step 6) — inconsistent mental model.
  - Raw `st.json(result)` output dumped for validation cycle and version comparison (`:210`, `:674`) — unparsed, unfriendly.
  - Many manual button-driven steps ("Ingest GW results", "Run Validation Cycle", "Generate Weekly Report") — fragile, must be clicked in order with no guidance if skipped.
  - This page is **for engineers**, not the FPL player; the average user cannot interpret R² or CI coverage.

### 2.9 Model Comparison — `pages/8_Model_Comparison.py` (V3 shadow model evaluation)

- **Purpose:** Scientific V2-vs-V3 comparison + per-player explainability.
- **User goal:** *"Should I trust V3? Where does it disagree with V2, and why?"*
- **Components:**
  - Controls row: **Gameweek selectbox**, "Persist V3 to ledger" **checkbox**, **Run Comparison button** (action-gated page) (`:221`)
  - **Evidence banner card** (level, validated GWs, next tier) (`:92`)
  - 5 alignment **metric cards**: Players Compared, Correlation, Mean |Δ|, Mean Δ, Agreement Rate (`:289`)
  - **Scatter plot** V2 vs V3 colored by signed delta + perfect-agreement line (`:336`)
  - **Largest Disagreements** table + horizontal delta bar chart (`:373`)
  - **Explainability panel**: player selectbox, xPts projection card, **raw `st.json` contributing factors** (`:468`), xPts/90, expected minutes, start probability, minutes factor, rotation-risk badge, data quality, **component breakdown bar** (goals/assists/CS/bonus/other), 80%/95% CI metrics (`:418`)
  - **Recommendation differences**: captaincy (agree/disagree banner + top-3 tables), transfers + undervalued shared-pick comparisons (`:534`)
  - **Evidence ladder** (weak→statistically_significant with GW thresholds) + Key Insights (`:610`)
- **Data displayed:** alignment stats, V3/V2 projections, contributing factors, captain/transfer/undervalued differences, evidence level.
- **UX concerns:**
  - **Requires pressing "Run Comparison"** — the page is empty until then; no cached/auto report.
  - Contributing factors rendered as **raw JSON** (`:469`) — the most important explainability data is the least designed surface on the page.
  - Terminology again advanced (xPts, CI, correlation) with minimal inline translation.
  - "Persist V3 to ledger" is a write/administrative action placed beside a browse control without a confirmation.
  - Two-column dataframes (V2 vs V3) get visually cramped.

## 5. Data Availability Audit

Everything below is already queryable and frontend-renderable today.

### 5.1 Player Data
Name, first/second name, **team**, **position** (GKP/DEF/MID/FWD), **price (£m)**, minutes, goals, assists, clean sheets, bonus, BPS, influence/creativity/threat/ICT, **xG, xA, xGI, xGC**, **xGI/90**, points/£m, **form**, **ownership %**, transfers in/out (event + season), status/news, price changes, saves, set-piece orders.
→ Source: `database/crud.py:70` (`get_players_dataframe`), `services/player_service.py:12`.

### 5.2 Derived Scores
**value_score**, minutes_score, xgi_score, **minutes_fraction**, team_strength_raw, fixture_score_raw, set_piece_raw, finishing_ratio, creative_ratio, price_direction, net_transfers, ownership_tier, transfer_velocity, starts_rate, minutes_reliable, **fixture_score_3gw**, fixture_avg_1/3/6gw, home_count_next_3, fixture_easy/hard_count, **fixture_swing**, **is_penalty/fk/corner_taker**, form_tier, form_momentum.
→ Source: `services/scoring.py:29`, `features/store.py:405` (`build_feature_store` → `all_features()`).

### 5.3 Fixture Data

## 6. User Workflow Analysis

### 6.1 Weekly FPL Decision Workflow (primary)

```
Open app (About)            → friction: landing page adds a hop
  ↓
My Team (squad, captain)    → friction: captain shown as "Value Score", no reasoning,
                             no fixture context for the squad
  ↓

                             "Value Score" unexplained
  ↓
Assistant Manager (transfers, chips)
                            → friction: heavy load, plain-markdown exec summary,
                             long scroll, no captaincy surfaced here
  ↓
Player Comparison (A vs B)  → friction: 9 sections, static table, fixture slider bug
  ↓
Decision (action taken in FPL, off-app)
```

**Friction points:**
1. **No decision support on the decision page** — captaincy is split across page 1 and page 8, not on the Assistant Manager page where transfers/chips live.
2. **No "why"** — value scores, projected points, and recommendations are never explained on pages 1, 2, 5, 6.
3. **No fixture context on the squad** — the single most important FPL input.
4. **Vertical mile** — every page scrolls; no tabular summary of "what to do this week".

**Missing information:** a single "this week" briefing; projected points (not just value) for the user's squad; captain with reasoning; transfer window countdown; confidence on every recommendation.

### 6.2 Seasonal Strategy Workflow
Team Analysis (club strength) → Player Comparison (targets) → Player Rankings (prices/ownership) → Assistant Manager (future plan). **Missing:** any long-horizon view tied to the user's bank/transfers.

### 6.3 Model Validation Workflow (post-GW, technical)
```
Model Analytics
  Tab 1: Ingest results (button) → Run validation cycle (button + st.json)
  Tab 2: Scatter/MAE/RMSE      Tab 3: calibration + health
  Tab 4: error analysis        Tab 5: engine scorecard
  Tab 6: version comparison (button)   Tab 7: weekly report (button)
```

**Friction:** fully action-gated (page is blank until "Run Comparison"); explainability buried under a `st.json`; persistence checkbox conflated with browsing.

## 7. Technical Constraints (affects any redesign)

1. **Streamlit's rerun model** — every widget interaction reruns the whole script top-to-bottom; no client-side state, no URL routing, no custom navigation (pages auto-order from `pages/N_*.py`). Page-to-page navigation is limited to `st.page_link`/sidebar links.
2. **No component library** — all custom "cards" are raw HTML strings in `st.markdown`; no React/Vue, no styled-components; limited to Streamlit's widget set + Plotly.
3. **No auth, single-user** — team ID is a constant (`utils/constants.py:56`); no per-user state; any future multi-user work requires auth + a data sharding strategy.
4. **No backend/frontend separation** — Python runs everything in-process; Streamlit pages call services/DB directly. A dedicated frontend would require exposing a REST layer first.
5. **SQLite single-file DB** — `data/moneyball.db`; concurrent multi-user writes would break; WAL mode enabled but this is inherently single-writer.
6. **Live FPL API dependency** — data freshness driven by a 1-hour staleness tracker (`utils/helpers.py`, `components/sidebar.py`); no DB cache of raw API payloads; FPL API rate limits + retry logic in `services/api_client.py`. UX must handle empty/stale states gracefully.
7. **Heavy synchronous compute on page load** — Assistant Manager and Model Comparison run full pipelines inside `st.spinner` (`6_Assistant_Manager.py:42`, `8_Model_Comparison.py:249`); no background jobs, no progress persistence.
8. **Streamlit version pinned** (1.60) — features like `st.tabs`, `st.dataframe` config are available, but newer components (st.navigation, st.connection) depend on upgrade decisions.
9. **CI/CD** — `.github/workflows/ci.yml` now runs lint, dependency checks, secrets scan and tests on every push/PR; there is still **no Docker image or containerised deploy target** — deployment remains documented-only (`docs/deployment.md`) and the app is not yet publicly hosted.
10. **No screenshots/visual regression tooling** — no Playwright/Streamlit app testing in `requirements-dev.txt`.

## 8. Current UX Problems (prioritised)

### Critical
1. **Recommendations are unaccountable.** Every page surfaces scores ("Value Score", projections, ratings) with **no explanation of what they mean or why they differ** — yet explainability data already exists (contributing factors, confidence, evidence level) and is only shown on page 8 (and then as raw JSON).
2. **Engineering vocabulary leaks to end users.** MAE/RMSE/CI80/coverage/bias/version_id/Δ appear un-translated on pages 7 and 8; the "make analytics trustworthy" goal is undercut by jargon.
3. **Decision page doesn't carry decisions.** Captaincy (the highest-stakes weekly choice) is never shown on the Assistant Manager page; no consolidated "this week" view exists.

### High
4. **Vertical-mile pages.** Pages 2, 5, 6 stack 6–9 full-width sections; users must scroll past market charts and cards to reach conclusions. No progressive disclosure (tabs/expanders) except page 7.
5. **Duplicate/raw renderings.** Charts + tables of the same data (pages 2, 4); raw `st.json` (pages 7, 8); plain-text exec summary (page 6).
6. **Hidden filter labels.** `label_visibility="collapsed"` on sidebar sliders/multiselects (`components/sidebar.py`) → controls without labels.
7. **Inconsistent components.** `st.table` vs `st.dataframe`; inline HTML duplicates of `player_card`/`fixture_widget`/`charts`; ad-hoc empty states instead of the existing `render_empty_state`.

### Medium
8. **Manual, ordered validation flow** on page 7 with fragile state and empty-state confusion if steps are skipped.
9. **Page 8 gated behind "Run Comparison"** with a persistence checkbox mixed into the browse UI.
10. **Latent runtime bugs** affecting trust: page 5 fixture slider `min_value=5, value=(1,10)` (`5_Player_Comparison.py:323`).
11. **Evidence levels communicated inconsistently** — emoji+text (7), banner card (8), none elsewhere.

### Low
12. **About page is a dead-end** — hero cards not clickable, no story, no validation narrative.
13. **Unused built components** — `render_empty_state`, `render_metric_grid`, `position_tag`, `render_player_cards`, `render_fixture_score_bar/heatmap` are implemented but not wired, while pages hand-roll equivalents.
14. **No player detail view anywhere** — there is no single-player "story" page despite all the data existing.

## 9. UX Opportunities (based on existing capabilities)

1. **"This Week" briefing (highest value).** A top-of-app summary: squad with next-GW fixtures + difficulty, captain recommendation with *projected points and reasoning*, transfer suggestions, chip status, deadline countdown. All data exists (`team_service`, `fixture_service`, `captain_engine`, `opportunity_engine`).
2. **Explainability everywhere, not just page 8.** Attach "why" expanders/badges to every score: value score = weighted blend (weights already in `config/weights`), projections = component breakdown (already computed), recommendations = reasoning strings (already generated by `assistant_manager/explainer.py`).
3. **Trust signals.** Evidence badges (weak→statistically_significant) on any claim; "shadow model" tag on V3 outputs; model-health summary (from `get_model_health`) surfaced on recommendation pages so users know how much to trust them.
4. **Player storytelling.** A single-player panel (select any player → stats, derived scores, fixtures with difficulty, projection + CI + components, prediction-vs-actual history from the ledger, verdict). All data exists; page 8's explainability panel is the seed.
5. **Model comparison → recommendation.** Page 8's alignment/agreement already computes captain/transfer/undervalued differences; surface a one-line "V2 and V3 agree/differ" verdict inside Assistant Manager.
6. **Prediction history / version timeline.** The ledger stores per-GW projections + actuals; a player/version time-series would turn page 7's scatter into a story.
7. **Reduce verbosity, raise signal.** Reuse `charts.py`/`fixture_widget.py`/`player_card.py`; collapse chart+table pairs; replace raw JSON with designed components.
8. **Guided validation.** Replace page 7's manual ordered buttons with a stepper/wizard that detects next required step (finished GWs to ingest are already detected by `detect_finished_gameweeks`).
9. **Decision log as "receipts".** `decision_log` stores every recommendation + outcome; a "how accurate was our advice?" view is a powerful trust signal and is currently unused in the UI.

## 10. Future Frontend Recommendations

### 10.1 Stay in Streamlit (temporarily)
- **Exploration/analytics surfaces:** Player Rankings, Team Analysis, Team History, Player Comparison, Model Analytics, Model Comparison. Streamlit's rerun model fits read-heavy, filter-driven exploration; the existing Plotly + dataframe stack is working.
- **Iterate the design system here first** (tokens, cards, badges, tables) since all visual primitives live in `components/theme.py`.

### 10.2 Move to a dedicated frontend (when decision flows mature)
- **High-intent decision experiences:** "This Week" briefing, Assistant Manager (transfers/captaincy/chips), squad action view, player detail/story page.
- These need fast targeted reads (a squad + its fixtures + projections), persistent state, push updates (deadline countdowns, price-change alarms), and low-latency interaction — a poor fit for whole-script reruns.

### 10.3 API requirements (prerequisite for a frontend)
Expose existing in-process services as a thin REST/JSON layer, versioned per config:
- `GET /players` (+ filters/sort), `GET /players/{id}/projections`, `GET /players/{id}/fixtures`
- `GET /team`, `GET /team/picks/{gw}`, `GET /team/transfers`
- `POST /assistant/run` (squad evaluation, transfers, chips)
- `GET /versions`, `GET /versions/{id}/metrics`, `GET /comparison/v2-v3`
- `GET /report/weekly/{gw}`
All of these map 1:1 to existing services (`player_service`, `team_service`, `assistant_manager.engine`, `learning_service`, `comparison_reports`).

### 10.4 Potential component architecture
```
design-tokens (colors/type/spacing/radius)      ← already exists in theme.py
  └─ primitives: Card, Metric, Badge, Tag, Button, EmptyState
  └─ data display: DataTable (sortable/filterable), StatRow, Sparkline
  └─ domain: PlayerCard, FixtureBadge, DifficultyHeatmap, ProjectionCard,
             EvidenceBadge, ComponentBreakdown, ConfidenceGauge
  └─ decision: RecommendationCard, TransferCard, CaptainCard, VerdictBanner
```

### 10.5 Design system considerations
- **One type ramp** already defined in `theme.py` — promote to CSS custom properties consumed by a real component API (not raw HTML strings).
- **Semantic color roles** already defined (market/risk/quality/fixture) — enforce via the component layer instead of inline hex.
- **Evidence as a first-class visual language** — a single badge component reused for model evidence, confidence, and data quality.
- **Number formatting standards** — prices (£X.Xm), points (1dp), percentages, CI ranges rendered uniformly.
- **Dark-only today** — decide whether to support light mode before building the token system.
- **Accessibility gaps to close in redesign:** slider labels hidden via `label_visibility`, emoji-only status indicators, color-only risk semantics (add shape/text where color is the only differentiator).
